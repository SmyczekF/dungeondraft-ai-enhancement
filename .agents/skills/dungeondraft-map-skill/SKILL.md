# Dungeondraft Map Skill

Build a believable place that supports movement, decisions and encounter objectives. Prioritize TTRPG playability, then realism, then fidelity to the concept. Deliver an editable native map and correctly scaled VTT artwork.

## Workflow preferences

At the start of map work, resolve the working project's Git root and read `<repo-root>/map-workflow.json`, including when this skill is installed outside the repo or the working directory is nested. Do not read a second copy from the skill's install directory. If the project has no Git root, use an explicitly identified project root; if no file is present, use the defaults below. Explicit user instructions override these preferences. Read the file as JSON booleans, not strings; report invalid values or unknown keys and do not use them to expand the task.

`map-workflow.json` is local and Git-ignored. The tracked `map-workflow.example.json` is a setup template; initialize a missing local file from it when useful, but never overwrite existing preferences or treat the example as an override. Keep personal settings out of commits.

- `automatic_open_maps` (default `true`): perform necessary `create_map`/`open_map`/`reopen_map` lifecycle actions, including editor startup/restart. When `false`, present the concrete action, target dimensions/path and preservation plan and wait for approval unless that action is already explicitly approved. A general map brief alone does not bypass this checkpoint; an explicit instruction to open the identified map does. Do not make manual opening the default.
- `automatic_concept_approval` (default `false`): after showing the generated concept, **ask the developer to approve that displayed design and wait for an explicit reply before creating or populating its native map**. A general map request, silence or elapsed time is not approval. When `true`, continue after showing and reviewing the preview unless the user explicitly requests approval. This flag never skips concept generation or visual review. Approval applies to the same design; a materially replaced concept needs a new decision, while routine native corrections/export do not need another concept.
- `automatic_exports` (default `true`): after native visual review, generate the final files included in the authorized workflow. When `false`, show the reviewed map and proposed deliverables and wait for approval unless those concrete exports are already explicitly approved. Internal review renders and preservation saves remain part of the authorized work. This flag does not select Foundry delivery; `export_to_foundry` does.
- `reasoning` (default `true`): include concise design rationale for size, layout, routes and tactical choices in the existing concept handoff/notes. When `false`, omit this extra explanation; still plan dimensions and verify the result.
- `enhancing` (default `true`): apply the tactical-feature default under TTRPG design and add fitting exploratory/decorative improvements within the brief. When `false`, build the requested functional place without unsolicited extras. Both settings retain correct scale, connected routes and the mandatory visual correction loop.
- `export_to_foundry` (default `false`): when `true`, include Foundry file delivery and invoke the companion export skill. When `false`, export to Foundry only on an explicit request or established session requirement. A request for image-only output overrides this default. This flag does not authorize uploading, publishing, installing modules or changing a live Foundry world.

Keep checkpoints independent: approving a concept does not itself approve a lifecycle/export action that is configured to wait. Combine concrete actions ready for approval into one question where useful; after approval, continue native construction and its correction loop without asking for every placement.

The legacy `fully_automatic` key is removed. When migrating a local file, report its replacement: remove it, fill missing `automatic_open_maps`/`automatic_exports` from its boolean value and missing `automatic_concept_approval` with `false`. Preserve already configured granular keys and other preferences; never infer concept approval from the old flag. Report an invalid legacy value rather than guessing.

These preferences are read by the agent through the skills; the MCP server does not load this JSON automatically. If configuration is invalid, report it, continue work clearly authorized by the user, and resolve the affected preference before taking an action whose scope is uncertain.

## Map output directory

- In the `dungeondraft-ai-enhancement` workspace, resolve the Git repository root and put all map output under `<repo-root>/dd-maps/<encounter-slug>/`. Resolve this from the repository root even when the working directory is nested; do not write maps inside `server/`, `mod/` or the skill folder. An explicit user destination takes precedence.
- Keep the native map, final floor images, concept preview, concise play notes and current layout manifest together in that encounter directory. Any required project bundle or VTT export directory must also stay inside it.
- Keep one canonical native map per encounter and replace its current floor exports when revising it. Reuse the existing encounter directory and native filename; do not create backup maps, older versions, numbered revision folders or per-edit journals unless requested. If a project bundle is needed, choose its native map as the canonical file rather than keeping another final native copy.
- If the repository root cannot be determined, resolve the intended workspace before saving instead of guessing a different output location.

## Start here when no map is open

- Before creating or opening a map, estimate the required width and height in squares from the requested setting, encounter footprint, feature sizes, playable routes and square scale. This sizing analysis can be done without a live bridge or open map.
- Choose a compact canvas that comfortably fits the actual design at believable scale, with enough room for movement and useful surroundings. Do not default to an enormous map or add large empty margins; use larger dimensions only when the requested location or encounter needs them. Respect explicitly requested dimensions and explain any fit problem rather than silently changing them or shrinking important features.
- After the concept approval checkpoint and any required lifecycle approval, use `create_map(width, height, path, bootstrap_path=...)` when available to launch a blank native template, resize and save it. Use `DD_BOOTSTRAP_MAP` or a known blank native file; inspect existing workspace templates before requesting setup. If the current map is confirmed blank, it can be saved once as the bootstrap. Keep template/output maps under the workspace map directory. Use `open_map(path)` for an existing map and `reopen_map()` to save and restart the current named map. A closed editor can be started through these lifecycle tools. Check readiness before editing; request only setup that available tools cannot complete.

## Tool and interaction defaults

- Use **Dungeondraft MCP** for every operation it supports: asset discovery, placement, levels, camera inspection, saving and export. Check live capabilities instead of inventing tools or copying stale parameters.
- Follow `automatic_open_maps` for lifecycle checkpoints and `automatic_exports` for final file generation; neither overrides the concept checkpoint. Preserve the current map: lifecycle tools save its named file; for an untitled map provide a new `save_current_path` in its encounter directory when that destination is established. For preservation, ask only if a decision remains unresolved. Use computer use only when the user explicitly authorizes it for the task, and still prefer MCP where available.
- For a reachable bridge, call `ping`, then `get_status`, then `get_capabilities` before live edits; require protocol 23 and an open map. If the initial ping fails, one `open_map`/`create_map` call using a known native file/bootstrap is allowed after any required lifecycle/concept approval. The controller can start a closed editor and rejects a running editor whose bridge is unreachable. After success repeat the handshake. After a failed lifecycle call, inspect its error and retained file/log; ask only for the exact unresolved setup or manual action. Do not retry blindly or make manual startup the default.
- Preserve unrelated maps. Use a new encounter directory for a new map; revise an existing encounter at its canonical native path. Read the applicable project AGENTS.md and bridge documentation when available.

## Before every new map: generate a concept image

1. Extract the requested setting, map dimensions, priority features, encounter purpose, art style and scale. Resolve only missing details that materially change the result; state reasonable assumptions for the rest.
2. **Generate and show a preview image before creating or populating the new native map.** Use the available image-generation tool and its skill. An existing user-approved generated preview for this map satisfies this step. If image generation is unavailable, ask how to proceed rather than silently skipping it.
3. Prompt for a **strict orthographic overhead battlemap**, with no horizon, perspective, isometric buildings, labels or baked creature tokens. Include the intended footprint, realistic relative sizes, playable routes, room interiors and important terrain. Match the installed asset style where practical.
4. Inspect the preview. Fix perspective or proportion errors that would mislead construction. Treat it as a concept, not an exact placement diagram or guaranteed reproduction by native assets. Correct unrealistic details during native construction rather than copying them faithfully. Translate it into tile coordinates and a level plan. Apply `automatic_concept_approval`: by default show this preview, ask for developer approval and wait. Do not create or populate the proposed native map while that decision is pending. With automatic approval enabled, proceed after showing/reviewing it, subject to any separate lifecycle checkpoint. An already approved preview for the same design satisfies the checkpoint.

## Scale and believable places

- Default to **one square = 5 ft × 5 ft** unless explicitly changed. Native coordinates use **256 woxels per square**. Keep feet, tiles, woxels and exported pixels distinct. Record the scale in the deliverable.
- Before committing to a layout, check that the available map dimensions fit the requested features at believable scale. `resize_map` supports only blank single-level bootstrap maps and clears history; save after resizing. Choose final dimensions before populating. For an existing populated map, preserve its content and assess a layout correction within its canvas. If a larger canvas is essential, explain the unsupported populated resize and ask for the preservation/design decision; do not simply ask the user to open a different map. Do not shrink important features merely to fit the current canvas.
- Derive object scale from asset texture dimensions/footprints; do not enlarge trees, furniture, cages, doorways or ships merely to fill empty space. For this user, prefer readable chair artwork around one square rather than a quarter-square; this visual convention overrides literal furniture proportions and does not imply a one-square collision footprint. Preserve usable structural routes without over-optimizing clearance around ordinary movable props.
- Check that closed door leaves meet both jambs without visible gaps; match the artwork to the opening and wall thickness, beyond merely mounting a portal. Size windows to the building and room proportions rather than defaulting to tiny openings.
- Give each room a purpose and furnish it accordingly: sleeping, cooking, storage, work, guard duty, worship, sanitation or another stated use. Consider access, supplies, privacy, smoke, light and structural support as relevant.
- Furnish sleeping areas for their occupants and purpose: a rough pirate hideout can use casually angled camp beds and shared storage, without a tidy desk and chair in every bunkroom. Where sitting tables fit the setting, provide usable tabletop space and matching chairs.
- Make service areas visibly functional at a level suited to their occupants and resources. For an operating tavern, include stocked storage/display behind the bar and serving items such as mugs, bottles, pitchers or food on the counter. Preserve the staff working aisle and a coherent kitchen/storeroom route; avoid decorative counters with no supplies or equipment.
- Make paths follow actual travel between destinations. Explain shortcuts through terrain, worn use, maintenance access, a breach or another believable cause. Connect stairs, ladders, landings and doors to usable space on both ends. Check the full painted path width around walls and corners, not only its centerline; a path must meet a real opening when it enters a building.
- Avoid implausible intersections with fireplaces or fixed construction; small movable props may partly overlap a route without requiring a layout redesign or VTT collision. Fit table lamps/candles entirely on the tabletop, usually near a corner to leave usable space; inspect actual sprite footprints after changing table size or rotation. Put serving props on the visible solid surface of a counter or shelf; the empty interior of a U/L-shaped counter and transparent sprite padding are floor space. Do not add collision around serving props or ordinary counters merely because their artwork occupies floor space.
- **User lighting preference:** omit ceiling-lamp artwork from playable floor maps and retain only its light emitter. Visible wall lamps or torches must sit against a wall; table fixtures must visibly rest on furniture. Do not place a hanging-lamp sprite in open floor space.
- Poverty does not imply total destruction. For occupied poor settlements, use **makeshift or patched walls**, salvaged planks, canvas or intact simple construction as the setting warrants. Include genuinely ruined structures only when their history supports damage. Vary condition and footprint where plausible; keep enough wall/support to shelter occupants and hold remaining roofs. Place rubble and fallen beams where damage occurred, integrated with the surrounding ground.

## Natural irregularity and intentional order

- Group vegetation by habitat and foot traffic: dense patches, loose edges and open or cleared ground. Vary spacing and believable tree/shrub sizes; avoid evenly scattered miniature plants. Keep routes usable and let greenery support cover and visibility.

- In both concept images and native placement, usually favor gentle, purposeful irregularity over ruler-straight lines, repeated right-angle turns or perfect rows. Let paths wind between destinations, buildings and terrain; vary building orientation, spacing and footprints where settlement history permits. Shape natural shorelines with uneven curves, coves and outcrops, avoiding long straight segments or obvious angular joins unless the coast is engineered. Use soft terrain transitions and irregular vegetation clusters rather than isolated square rock patches or uniform scatter.
- Small, varied rotations and offsets often make furniture, crates, rugs and other movable props feel used and believable. Keep fixed installations, fitted furniture, walls and doors aligned where construction requires it. Preserve structural coherence, usable entrances and token-scale movement; do not apply random rotation to everything.
- Decide how much order the setting supports. Planned cities, formal gardens, engineered docks, disciplined camps and carefully maintained interiors may reasonably have straight routes and aligned structures. Natural irregularity is a default, not a ban on geometry: vary details only where their use, terrain or history supports it. During visual review, check for accidental grids, identical orientations and unnaturally straight coasts; correct them when the setting does not justify them.

## TTRPG design

Consult the **2024 Dungeon Master's Guide**, especially encounter objectives, dungeons, environmental effects, hazards, traps, doors and combat encounters. Refer to the **2024 Player's Handbook** when movement, combat, cover, visibility, climbing, jumping or other player-facing rules affect the design. Read [references/ttrpg-design.md](references/ttrpg-design.md) for official sources and a focused review checklist. Use another system's rules when requested. Distinguish verified rules from encounter suggestions; do not fabricate book text, page numbers, damage or DCs.

When `enhancing=true`, **include at least one clearly readable tactical feature by default** (difficult terrain, useful cover, meaningful elevation or another fitting interaction); omit it only when it clearly conflicts with the place, and briefly explain that exception in the notes. Actively look for natural opportunities for elevation, difficult terrain, cover, environmental interactions, alternate routes and secrets while planning. Decide which belong, how many there are and how elaborate they should be from the setting, physical footprint, occupants, construction history and requested encounter. With `enhancing=false`, include requested features and those needed for a coherent, usable place; skip optional additions from the guidance below. Omit features that would feel forced or unnatural. A small simple hut may be flat, have one entrance and contain no difficult terrain or secret rooms, while its surroundings may offer suitable tactical features. A larger complex may plausibly have service corridors, concealed passages, private rooms and several routes. Do not enlarge or complicate a place merely to fit every feature.

- **Verticality:** consider ledges, ramps, stairs, balconies, pits or raised positions where they fit. Elevation is one tactical option, not a higher priority than readable difficult terrain or cover. A genuinely flat location can remain flat. Where height matters, provide plausible access and relevant counterplay; record heights in feet, transitions and fall risks. Height alone does not grant an invented automatic combat bonus.
- **Difficult terrain:** actively look for appropriate mud, unstable rubble, deep sand or undergrowth and use it to create meaningful movement decisions. Choose its extent from actual conditions; omit it where the place does not support it. Offer alternate routes when they fit; an intentional crossing or bottleneck may require traversing it. Show designated difficult terrain with a distinct material/texture and fitting clutter, such as gravel plus a coherent rubble patch; record its bounds in the manifest/DM notes. Low loose stone clusters can slow movement without collision or vision walls; isolated pebbles do not automatically define a zone. Make that constraint readable and plausible. Separate slow movement from impassable obstacles and hazards; ordinary dirt is not automatically difficult terrain.
- **Cover and visibility:** block movement only where passage is logically impossible, such as solid walls, genuinely large boulders or substantial fixed structures. Beds, desks, tables, barrels and small rocks normally need no collision; the GM can treat awkward footing as difficult terrain during play. Judge sight separately from movement, using actual height, size and opacity: ordinary low furniture need not hide tokens, while tall ovens, opaque tents or huge rocks may. If uncertain, add neither movement blocking nor sight occlusion. Cover is a separate GM rules decision and need not add either restriction. Keep structural boundaries/openings precise and record only meaningful exceptions; see the companion export reference for implementation.
- **Secret spaces and alternate routes:** strongly consider opportunities for them, especially in larger or more elaborate places. Include them when there is room and a believable purpose, such as maintenance, escape, concealment or restricted access. Ordinary buildings need not have them. Keep secret rooms and passages on their actual playable floor, with concealed access and discovery information in DM notes. Conceal every exposed entrance, including exterior escape mouths, with plausible matching artwork and, when exporting to Foundry, closed Secret Doors; inspect from both sides. Fog of war alone does not disguise an opening once the surrounding area is visible. The user will hide unexplored areas and secrets with VTT fog of war or visibility controls; do not create separate secret/GM native levels or duplicate player/GM artwork by default. Keep secret labels and rules annotations out of the map art.
- **Environmental opportunities:** actively look for and usually include interactions the place naturally supports, such as ropes, cargo, movable cover, water, fire or mechanisms. Choose relevant ones rather than adding an interaction of every kind. Omit contrived additions. Make their purpose and possible consequences clear in DM notes.
- **Rules-based lighting:** identify each actual light source and its state, verify its bright radius and additional dim distance in the requested edition (D&D 2024 by default), and retain those values with a source citation for VTT export. Native light size/color is an artistic setting, not evidence of a rules radius. Where no specific rule exists, label the chosen illumination as a GM ruling rather than presenting an analogy as RAW.
- Support the requested encounter with the relevant entrances, destinations, routes, information and possible solutions. Multiple exits, bypasses and noncombat solutions are design choices, not mandatory fixtures. Do not turn a map-only request into a full statted encounter unless requested.

## Native levels and drawing layers

Plan levels before placement. **Use separate named native levels for true upper floors and basements**, aligned with the ground footprint. Keep all rooms, including secrets, on their actual floor. Terrain elevation can remain geometry on Ground when no overlapping floor is needed; record its height separately.

**User stair-art preference:** keep the dark end toward the bottom of the image and use consistent shading/orientation for the same stair on both floors. Record actual ascent, descent and landing positions separately; do not reverse the graphic merely to denote another floor.

**User default for future maps:** omit decorative roofs, separate roof levels/layers and roof exports. Unrevealed buildings will appear black through VTT fog of war or visibility controls, so roof artwork is unnecessary; retain the playable interiors underneath. Add a roof view only when explicitly requested, or a true rooftop floor when it is part of the requested playable encounter. Apply these defaults to new work; do not remove existing secret or roof levels merely to enforce them.

Within each level, use distinct native components and drawing layers for terrain, water, floor patterns, paths, props, foliage and overhead details. Drawing order and native floors are different controls: setting a roof/object to a high Z value does not put it on a separate floor. Native water should remain editable water; a visual path should not become a giant opaque ground prop.

Read [references/mcp-workflow.md](references/mcp-workflow.md) before level creation, batching or export. Maintain a label/ID/index map; adding a floor shifts indices. Confirm the active level before each placement batch. Do not flatten true playable floor separation merely to satisfy an export limitation. Explain the gap and export supported floors individually or request the specific user action needed for a combined view.

## Optional Foundry VTT delivery

When the user requests Foundry preparation/export or `export_to_foundry=true`, also use the companion [dungeondraft-foundry-export skill](../dungeondraft-foundry-export/SKILL.md), if available. It can be used during creation or later with an existing map. Use the supported Foundry 14 file route by default when no other target is established; clarify only a version/system/scale conflict that changes delivery. With `export_to_foundry=false`, ordinary map requests do not require choosing a VTT or loading that workflow. Keep generic map creation and floor-art exports usable without the companion skill.

## Build, inspect and deliver

- Prefer `plan_battlemap`/`apply_battlemap` where the live planner supports the design. Inspect warnings and preserve the semantic/native-ID manifest. Use low-level MCP tools for native floors, patterns, roofs and other unsupported details; keep each planner record tied to its original level.
- Batch repetitive placements with `apply_batch`, respecting live operation limits and stable idempotency keys. Keep job IDs and inspect completion/results. Start with ground, routes and structural geometry, then key encounter features, then detail.
- **Complete the mandatory visual review and correction loop below** after building or revising the map and before delivery. Successful tool responses and structural validation do not establish that the map looks correct.
- Use `validate_battlemap` for applied planner projects when supported. Treat visual review and structural validation as separate evidence. Do not add software tests or edit MCP code merely to create a map.
- Save the native map. Apply `automatic_exports` before final file generation; internal inspection renders remain allowed. Export gridless, top-down artwork for each actual playable floor at matching resolution and origin. Include its secret rooms in the same image for concealment in the VTT; omit duplicate player/GM and decorative roof exports by default. Preserve editability and identify what remains manual. A PNG does not include working VTT walls, light sources, elevation rules or tokens.
- Deliver clickable map/image paths, map dimensions, feet per square, pixels per square, floor labels and short DM notes for heights, difficult terrain, cover, hazards and interactive features. State whether VTT data was exported or actually imported. Finish only when the requested map is saved, playable and visually reviewed with no remaining glaring errors, within the stated limits. If a tool limitation or required user action blocks a correction, identify the unresolved issue and do not claim the map is finished.

## Mandatory visual review and correction loop

After completing construction or any revision, actively look for defects in the actual native map; do not rely on the concept image, placement coordinates or validation alone.

1. **Inspect the whole map and local details.** Use rendered previews and camera/screenshot tools at overview and playable/token scale. Inspect every playable floor, important rooms, entrances, routes, shores and elevation transitions, plus any explicitly requested roof or supported combined view.
2. **Recheck scale, realism and readability.** Compare buildings, doors, furniture, vegetation, terrain and routes against the recorded square scale and creature-token footprints. Look for implausible cliffs or rock formations, height differences that are visually invisible or ambiguous, stairs/ramps without believable landings (omit them when no readable height change exists), beach sand hidden under a uniform cave-floor texture, invisible or disconnected paths, abruptly cut-off assets or repeated terrain segments, gaps, overlaps, floating props and incorrect drawing order. Elevation should read through coherent edges, cliff faces, shading and access; routes should remain visible and physically usable where intended. Check that each designated difficult-terrain area is recognizable by material/texture, and every exposed secret entrance is disguised from both sides. Preserve deliberate secrets and setting-appropriate irregularity.
3. **Fix, then inspect again.** Correct identified problems in the native map, render fresh views and recheck both the changed area and its surroundings for new defects. Repeat this loop for as many passes as needed until a fresh review finds no glaring scale, realism, continuity or readability errors. One review pass or a fixed number of passes is not a completion criterion. Rerun structural validation when supported and relevant to the changes; it remains separate from visual review.
4. **Verify the delivered artwork.** Save the corrected native map, replace affected final exports and inspect the actual exported images for scale, framing, floor alignment, visibility and clipping. If an export reveals a defect, return to correction and review before delivery. Report any blocked correction explicitly; do not present an uninspected or visibly flawed result as complete.
