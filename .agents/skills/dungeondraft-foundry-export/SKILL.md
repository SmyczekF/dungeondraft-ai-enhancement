# Dungeondraft to Foundry VTT

Turn a Dungeondraft map into an explicitly versioned Foundry export with enough semantic information to correct import losses. Use this skill independently for an existing map or together with `dungeondraft-map-skill` when a new map is intended for Foundry.

## Workflow preferences

Resolve the working project's Git root and read `<repo-root>/map-workflow.json` before export work, including from nested directories or a user-wide skill installation. Use an explicitly identified project root if there is no Git root; do not substitute the skill's install directory. Missing files/keys use these defaults: `automatic_open_maps=true`, `automatic_concept_approval=false`, `automatic_exports=true`, `reasoning=true`, `enhancing=true`, `export_to_foundry=false`. Read actual JSON booleans; report malformed values or unknown keys and resolve an affected preference before acting on uncertain scope. Explicit user instructions take precedence.

`map-workflow.json` is local and Git-ignored. Use tracked `map-workflow.example.json` only to initialize a missing local file; never overwrite existing preferences, apply example values over them or commit personal settings.

- `export_to_foundry=true` includes Foundry file delivery by default. When `false`, an explicit Foundry request or established session requirement still invokes this workflow. An image-only request takes precedence. Use the supported Foundry 14 route when no other target is established; ask only about a target/system/scale conflict that changes delivery.
- `automatic_open_maps` controls necessary creation/open/reopen/startup/restart: when `true`, perform supported lifecycle steps; when `false`, present the concrete action and preservation plan and wait unless already explicitly approved. Keep lifecycle approval separate from concept/export approval; combine ready concrete choices when useful. Preserve unrelated work.
- `automatic_concept_approval=false` requires explicit developer approval of the shown concept before constructing a new map; the companion map skill owns this checkpoint. When `true`, it still generates/shows/reviews the preview. Exporting or routinely revising an existing map needs no new concept. Never infer approval from a generic map request or silence.
- `automatic_exports=true` produces the final files selected by the brief and `export_to_foundry` after review. When `false`, show the reviewed map and concrete export plan and wait unless those exports are already explicitly approved. A direct request to export an identified map approves that export; enabling `export_to_foundry` alone only selects delivery and does not bypass this checkpoint. Internal review renders and preservation saves remain allowed. Finish supported file delivery when runtime access is absent, once any required approval is satisfied.
- `reasoning` controls concise rationale in the existing export notes/handoff. `enhancing` controls optional additions during map construction; neither setting disables wall/light correctness, file validation or requested runtime checks. Exporting an existing map does not itself authorize redesigning it.

The legacy `fully_automatic` key is removed. Report/migrate it by preserving existing granular settings, filling missing `automatic_open_maps`/`automatic_exports` from its boolean value and missing `automatic_concept_approval` with `false`, then removing the old key. Never infer concept approval from it; report an invalid legacy value rather than guessing.

The agent reads this JSON through the skill; it is not a server runtime setting. These flags do not authorize installing modules, publishing, uploading to a server or mutating an unrelated live Foundry world. Continue clearly authorized work if configuration is invalid; resolve only the affected choice.

## Scope and entry points

- **Existing map / export later:** inspect the canonical map, available project bundle, layout manifest and notes. Assess what can be exported before changing the map. Do not regenerate a concept, recreate the encounter or require map-construction steps merely to export it.
- **New map for Foundry:** combine with the [map creation skill](../dungeondraft-map-skill/SKILL.md), if available. Plan restrictions, openings and lights before construction. The map skill owns concept/design/native visual review; this skill owns Foundry semantics, export and import acceptance.
- **Files already exported:** inspect their completion manifest, target version, image path and warnings first. Live Dungeondraft access is needed only for native inspection, corrections or re-export.
- Load this workflow when Foundry delivery is requested, clearly established by context or enabled by `export_to_foundry`. Apply configured approval checkpoints without adding a separate VTT-choice prompt to every map request. Default to the supported Foundry 14 file route when appropriate; clarify only a target conflict that affects the deliverable.
- **User default for every Foundry export:** always enable global illumination and set its darkness threshold to **0.8** directly in the delivered scene. For Foundry 14, set `environment.globalLight.enabled = true` and `environment.globalLight.darkness.max = 0.8`. Preserve this default when regenerating exports; an explicit user request for different settings takes precedence.
- **User import preference:** deliver one self-contained scene JSON with its background image embedded when the target Foundry version supports it. Validate the embedded image against that version's schema and image sanitization path. For the inspected Foundry 14 build, a `data:image/webp;base64,...` background is accepted and persisted as a normal asset during GM import. Prefer lossless compression at the original dimensions. Do not require a separate image upload or background selection for this route.

## Workflow

1. Read [references/foundry-vtt.md](references/foundry-vtt.md) for route selection, conversion limits and acceptance checks; read [the D&D 2024 lighting guide](references/dnd-2024-lighting.md) when choosing or correcting light profiles for that edition. Resolve game system, scale and floor arrangement from context and default an unspecified target to supported Foundry 14; ask only for a consequential conflict or missing input that changes the route.
2. For a reachable bridge, call `ping`, `get_status`, then `get_capabilities`; require protocol 23 and `map_open=true` before edits. If the canonical native map is not loaded, apply `automatic_open_maps`, then use `open_map(path)` to save the current map and start/restart the identified editor, then restore saved project ownership with `load_battlemap_project` before planner export. Use `reopen_map()` only when a restart is actually needed. For an untitled current map, supply an established new `save_current_path`; ask only if preserving it needs a decision. If initial ping fails, one authorized `open_map` call can start a closed editor; a running editor with an unreachable bridge is left alone by the controller. After success repeat the handshake. After failure inspect the retained file/error/log and request only the manual setup that tools cannot perform. Do not retry blindly or ask the user to open a map that lifecycle can load. Files already exported need no live editor. Inspect content before edits and prefer MCP; computer use still requires explicit authorization.
3. Preserve intended movement, sight, light and sound restrictions in existing encounter notes/layout metadata, with floor and native/semantic IDs or tile coordinates. Block movement only through genuinely impassable features. Ordinary furniture, barrels and small stones normally need no collision; awkward footing can remain a GM difficult-terrain ruling. Decide sight blocking independently of movement, based on height, size and opacity; low beds/desks need none. If uncertain, add neither restriction. Consider large rocks, tall ovens, opaque canvas or cage boundaries only where justified. Read the reference's **Tactical scenery and visibility** section before assigning these behaviors. For lighting, follow the requested game's edition (D&D **2024** by default), verify each source's rules and convert additional dim distance to Foundry's total dim radius; never accept decorative native light ranges as rules values. Record every secret entrance, including the exterior mouths of escape routes; conceal its artwork and use closed Secret Doors so either approach remains hidden. Record locks, window behavior, bright/dim radii and floor transitions that export may lose. Artwork is separate from functional VTT data.
4. Select an eligible export route. The examined repository adapter targets **Foundry 14**, a validated applied/restored **single-level** project, a square grid and **5 ft per square**. Native Universal VTT plus a compatible importer is an alternative. Do not invent planner ownership, flatten floors or silently change scale. If the requested route is unsupported, deliver supported artwork/data and precise remaining work.
5. Save and review any native corrections, apply the `automatic_exports` checkpoint, export, wait for completion and inspect the resulting files and warnings. Keep all output under `<Git-repository-root>/dd-maps/<encounter-slug>/`, including when invoked from nested directories, unless the user specifies another destination. Reuse the encounter's canonical native map; preserve needed project ownership and avoid backup/version folders by default.
6. Deliver a complete Foundry scene JSON with the requested wall/light corrections and embedded background for the user to import, following the preference above. Include the README's [click-by-click import instructions](../../../README.md#import-into-foundry-vtt) in the encounter handoff: create/name/save a scene, right-click its entry in the Scenes list, Import Data, choose `foundry-scene.json`, then optionally regenerate its thumbnail. Prefer this built-in handoff; do not require a script macro when the user wants to import/re-import the finished map. Use a current-scene patch only when preserving existing world changes is actually requested or needed. Correct conversion losses in the target runtime when access and authorization are available. File export alone does not prove successful import. Never rerun a scene-creation macro blindly after an uncertain result.
7. Apply the reference's player-view acceptance checks before claiming runtime verification. Deliver paths, target version, scale, corrections and unresolved items; distinguish **files exported**, **scene imported** and **runtime behavior verified**. When runtime access is absent, finish the requested file handoff and identify the pending import/checks clearly.

## Known conversion gaps

Native Universal VTT can omit natural cave boundaries: inspect LOS against the actual cave and restore missing contours from verified native geometry before claiming complete walls. The current adapter turns native portals into ordinary doors; windows, secret types and locks need explicit correction. Lights are approximate, and ambient illumination needs review. Cover, difficult terrain and encounter zones remain metadata; actors, tokens, game-system automation and automatic multi-floor transitions are not created. A PNG alone carries none of those behaviors. Recheck these limits against the implementation and capabilities when versions change.
