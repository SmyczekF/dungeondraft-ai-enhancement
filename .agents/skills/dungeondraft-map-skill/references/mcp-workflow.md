# Dungeondraft MCP operation notes

Read for level setup, repetitive placement, lifecycle operations and delivery. Load the working project's root `map-workflow.json` as described by the skill before choosing automation checkpoints or Foundry delivery. These notes reflect the 1.0.0 protocol 23 bridge; **live capabilities, tool schemas and project instructions take precedence** when versions change.

## Levels and layers

- `list_levels` returns native IDs, labels and current indices. `add_level(label=...)` creates a blank level at **index 0** and leaves the old level active. It does not copy the ground. Refresh the list after each creation; resolve the desired stable ID/label to its current index before `set_level(index=...)`. IDs may be reassigned when loading a saved map.
- Prefer Ground alone for elevations that hide no important playable content underneath; record heights and access without extra floor-switch controls. Create separate upper floors/basements when meaningful rooms or routes overlap, or when explicitly requested. Put secrets on their actual floor; use VTT fog of war to conceal them rather than separate secret/GM native levels or duplicate player/GM exports. Omit decorative roofs and roof levels/layers by default: unrevealed buildings will be black in the VTT. If the user explicitly requests a roof view or playable rooftop, align it with the building beneath. A new level may reorder the list; do not rely on creation order matching elevation.
- When an explicitly requested roof occupies a separate level, switching to its underlying floor exposes that interior. The examined bridge has no dedicated Compare Levels/opacity tool. Prefer supported per-floor exports when they satisfy delivery; request manual configuration only if an essential combined view cannot be produced with available tools. Computer use requires explicit authorization. Do not claim a screenshot proves a combined view unless actually inspected.
- Objects use `layer` in -1000..1000; floor patterns use native `z`. Paths use their own **0..3 layer indices**. These ranges are not interchangeable. Terrain and water have dedicated native components on each level.
- Example drawing order within a level: floor patterns below props, pier/deck floors above native water, cargo above those floors, foliage above ground details. Pick values for the scene; do not treat an old scene's numeric layers as universal architectural levels.
- For an explicitly requested roof, `add_roof` accepts a **ridge line**, not a perimeter. For a gable roof, span the full long axis and use half the short dimension plus modest eaves as `width` in woxels. Inspect coverage and alignment. Separate roofs at different orientations for an L-shaped building when appropriate.

## Placement and batches

Use `list_asset_metadata`/`list_assets` with category, substring, offset and bounded limits; discover actual paths instead of guessing them. For an asset width of 256 woxels, scale 1 spans one tile, or 5 feet at the default scale. Transparency padding can make texture size differ from its visible or mechanical footprint.

Get supported batch commands/limits from `get_capabilities.batch`. The examined version permits up to 500 operations but at most 16 terrain and 16 water operations per job, and restricts terrain brush radii within batches. Preflight rejection means no edits were accepted. Correct the payload; inspect a failed or uncertain accepted job before retrying. Retry uncertain submissions with the same key in the same bridge instance. Keep editor UI and active level unchanged during a running job.

Colorable assets may need explicit tint at creation. Inspect actual artwork rather than trusting names: a campfire log prop may need a separate flame, a hanging cage may differ from a floor cage, and a mud decoration can look like a blue pool. Use native patterns/floors, not opaque props as substitutes for rooms.

On curved walls, mount doors/windows in the middle of a straight span long enough for the opening and both jambs. Mounting at a polygon vertex can leave one side uncut or a frame detached from the wall. Portal `radius` controls the wall cut; do not assume the artwork stretches to fit an oversized opening. Match the cut to the visible asset and inspect both joins in a fresh native export.

For a pier or jetty, verify that its full usable width reaches dry land; a small corner overlap is insufficient. Check nearby prop support too: anchors and other heavy salvage belong ashore, on decking or visibly submerged, rather than apparently floating on the water surface.

## Lifecycle and exports

- The mod initializes after a map loads. Use Python-side `open_map(path)` or `reopen_map()` to save, restart the identified local Windows editor and verify the new bridge/process/path/dimensions. These tools work with populated maps by avoiding native scene replacement. Do not restart merely to change water colors: `set_water_settings` rebuilds existing water in place. For an untitled current map, supply an established new `save_current_path`; do not set `discard_current` without authorization to discard that work. Active batches/exports and incomplete saves block restart. Follow `automatic_open_maps` for any lifecycle action not yet explicitly approved; new-map construction also waits for the main skill's concept checkpoint. Preservation saves and internal review renders remain allowed; `automatic_exports` controls final file generation.
- If initial ping fails, after any required concept/lifecycle approval make one lifecycle call with the known canonical map or blank bootstrap. The controller can launch a closed editor and refuses to stop an existing editor with an unreachable bridge. After success repeat ping/status/capabilities. After failure inspect the reported state and retained file/log; request only the specific setup or manual action that tools cannot complete. Do not repeat uncertain calls blindly or default to asking the user to open/restart Dungeondraft.
- `create_map(width, height, path, bootstrap_path=...)` requires a new destination and a blank native template (or `DD_BOOTSTRAP_MAP`). It preserves the template, saves the current map, launches the new file, calls `resize_map` and verifies the saved dimensions. The bootstrap must have one level, default unpainted terrain, and no elements, water, caves, tiles or building shapes. Choose 1..200 tiles per side. A failed create retains and reports its destination; inspect it instead of retrying into the same path. Direct `resize_map` clears history and is restricted to blank maps; save afterwards. Do not call private `Master.CreateNewMap` or use populated native replacement.
- `save_map` confirms native JSON. Wait for saving/exporting and native save callbacks to finish before further lifecycle changes. Bridge history is separate from native Ctrl+Z; not every operation is undo-recorded.
- Planner records are bound to one bridge instance and native level. Save supported project bundles; after restart/load, restore ownership with the supported project loader before revising/exporting the plan. Do not fabricate a planner record for arbitrary manual edits.
- Native PNG export in the examined bridge targets the active level. Inspect its contents and dimensions; it is not automatically a composite of all floors. `export_battlemap` requires a validated applied/restored **single-level** project. Multiple-level VTT scene export and automatic roof/ground compositing are not established by that tool. Preserve the levels and deliver supported per-floor native exports. Request manual export settings only if essential requested output remains blocked.
- When an upper-floor image should reveal the lower surroundings, `set_terrain_settings(enabled=false)` hides that floor's terrain without deleting its paint and permits a transparent native export. Keep its full canvas, origin and resolution aligned with the other floors, and inspect actual alpha outside the floor plate. Keep terrain enabled on floors with native water: water over disabled terrain renders black in the inspected Dungeondraft 1.2.0.1. Transparent artwork alone does not configure VTT level visibility or floor surfaces.
- Review open-water exports at the canvas boundary as well as the shoreline. Full-canvas native water can produce an artificial bright rectangular edge. Adjust native colors and nonzero blending, then re-export and inspect; matching deep and shallow colors worked for a calm, uniform sea on the lighthouse map. Do not assume a zero blend setting is safe: it produced triangular rendering artifacts in that build.
- Respect native export bounds: 16 megapixels and 8192 pixels per side in the examined version. Choose pixels per tile from map size and verify the written PNG. A 30×30 map at 128 pixels/tile is 3840×3840 and represents 150×150 feet at 5 feet/tile.
- Deliver grid origin, resolution, per-floor alignment and gameplay notes. Treat VTT file generation and successful import into a target runtime as separate outcomes.
